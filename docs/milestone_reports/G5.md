## Usability validation (automated)
- **Keyboard:** Ctrl+1…6 switch areas, Enter sends chat, every button has an accessible name and keyboard focus (`tests/ui/test_g5_gui.py`).
- **Scaling:** real Windows Qt platform at the window's **minimum size 900×600**, `QT_SCALE_FACTOR` 1 / 1.25 / 1.5: the first run found **clipped button text on Projects/Tasks/Results at all three scales** (a real defect); fixed with a wrapping `FlowLayout`; re-run: 0 violations (`tests/windows/test_scaling.py`, screenshots `g5_screens/`).
- **Unicode / spaces:** full write workflow in `Dự án có dấu & khoảng trắng` with a Vietnamese data directory (real git + pytest).

## The "FOREIGN KEY constraint failed" popup you reported
Raised by `TasksPage._on_job` (an unexpected exception while running a work order). **I could not reproduce it** with: an upgraded G1-era database, new/existing/sub-folder/late-initialised repos, rework with and without exact resume, the GUI **Bắt đầu** button in write mode, and a real-Claude GUI-driven product run (all completed, `PRAGMA foreign_key_check` clean); no application database exists under `%LOCALAPPDATA%\AATPO` on this machine to inspect. A genuine FK defect of this family existed earlier in development (artifact rows for reports/diffs/test output referenced a non-existent run) and was fixed before the first G4 commit; a copy of the app started before that fix would show exactly this message. What changed so the next occurrence is diagnosable: tracebacks go to `%LOCALAPPDATA%\AATPO\logs\errors.log`, the work is stopped safely, and the popup names that file. **If it happens again, please send that log file (it is redacted) and tell me which button you pressed.**
